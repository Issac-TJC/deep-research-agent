# 面试深挖：实现、真实问题与证据边界

此文在核心功能实现后整理。开发过程的原始记录见 development-log。已完成多轮真实 DeepSeek/Tavily 联调并记录失败案例，逐轮结果见开发日志；本文不预填准确率、时延提升或多 Agent 收益。

## 1. 场景与项目价值

工程师比较中文技术知识库的关键词、向量、混合检索与重排方案，资料来自官方说明、论文和实验报告。困难在于实验条件不同、罕见错误码与语义问题需求不同、资料缺失和结论冲突。输出需要说明适用条件，并允许用户回到原文核对。

同一引擎支持论文研读：先让读者理解原理、实现流程和实验设计，再分析局限与可检验的研究方向。系统没有执行论文代码，也没有判断某个研究方向已经具有新颖性。

项目可展示的组合是：四角色协作＋来源版本／精确文本证据＋可恢复运行／预算／取消＋两租户隔离＋可复核工作台与评测入口。相对参考项目的定位来自固定版本源码分析；尚未运行它们的同条件性能对照，不能声称优于这些项目。

## 2. 为什么这样拆 Agent？

Planner 拆问题与依赖；Researcher 独立上下文执行有界 search/fetch/read；Reviewer 检查支持、遗漏、冲突和解释；Writer 只能写报告及授权局部修订。来源解析、鉴权、预算、调度和哈希由程序完成。

分角色的理由是权限、上下文和交接责任不同。是否比单 Agent 更好必须测：B0 单迭代 Researcher、B1 多 Researcher 无全局补证、B2 完整闭环，同模型、同语料、同总预算。Reviewer 与 Writer 使用同模型时并不统计独立，存在共同错误。

## 3. 上下文处理到底做了什么？

V1 实现工件外置、原文片段选择和在完成工具轮次边界重新构造上下文。冻结 brief、用户约束、任务目标、来源引用与未解决项留在持久状态中；研究事实不依赖一段持续膨胀的聊天历史。原文保存在对象存储，可按授权 source ID 和字符范围回读。

这属于应用侧上下文管理。DeepSeek 服务端的上下文缓存由供应商实现；本项目记录缓存命中 token，不修改模型 KV cache。初版未启用递归 LLM 摘要和自动跨 run 语义记忆；同租户可通过 upload_ids 显式复用来源。

信息丢失仍可能发生在检索遗漏、模型忽略、抽取错误或片段选择阶段。不能因为原文还在就宣称模型一定记住。测试检查否定条件、用户约束、页码及字符范围；快照记录选入／省略内容。真实任务已记录省略次数，但长期触发概率、质量影响及全文／片段成本差异仍待受控付费实验；单个 run 的比例不能推广。

## 4. 真实遇到的问题

### 搜索额度耗尽导致已读取证据未提交

首轮真实检索选型任务中，DeepSeek 一轮提出多次搜索，6 次搜索额度很快耗尽。动作账本证明 read_source 已成功，但 Researcher 在后续 search 预留失败时抛出 BudgetExceeded，跳过了 read_slices 的节点提交和 extraction，最终没有 claims。run ID 和原始指标保存在开发日志。

修复没有增加预算掩盖问题：单任务搜索上限限制突发占用；每轮向模型提供剩余预算；耗尽后隐藏 search，保留 fetch/read。预算拒绝作为工具反馈并保存，继续提取已读取证据。注入同样的 read＋多次 search 顺序，验证额度仍受限且已有证据能够提交。真实复测已保存 27 条 claims/spans，但后续累计 token 限制导致部分交付。由于响应和来源没有冻结，这只说明工程路径生效，不能用来宣称质量或成本的统计提升。

同时发现长中文报告在审查时超出应用侧上下文上限。字节上界估计不是供应商真实 token 数，原实现还遗漏了 system/schema 开销。修复保留协议空间、精简重复元数据，并把默认单次保守上界调整为 64k；不声称压缩了模型 KV cache，也不把提高上限称为已证明的 token 节省。

### 结构化响应错误过于笼统，无法还原根因

真实 Writer 连续三次校验失败，旧日志没有区分截断、非法 JSON 或字段类型错误，丢弃了失败响应，因而不能事后断言具体原因。新增受 RLS 保护的失败响应、脱敏 schema 错误路径、finish_reason；重试带修复反馈并重新预留增加后的输入额度。各角色使用不同输出上限；最终失败仍保留证据包。此处的真实挑战既包括模型输出约束，也包括诊断数据是否足以支持排查。

### 思考额度、原文重写和错误的上下文固定区

真实论文抽取曾连续返回 `finish_reason=length`、正文为空、输出约 4096 token。新增诊断证明 thinking 占用了全部输出额度；修复从 16k 结构化额度开始，截断时有界增长，并按完整请求重新预留。不能用最终 JSON 字数估计总输出。

后续论文能解释内容，但生成引文均无法精确回到原文。渲染对照发现 PDF 两栏顺序和词间距问题；调整解析后旧引文仍不匹配，不能只归因于版式。改为模型选 passage ID、程序复制原文并绑定偏移，真实复测得到 12 claims / 7 spans。模型仍可能选错支持片段，因此精确定位与语义支持是两套检查。

这轮还发现程序发布门禁太晚，表格缺引用没有进入可用的局部修订环节。共用结构检查提前到 Reviewer 路由前，按节点 ID 授权补引或改为未知。注入“模型审查全部通过”的用例，验证程序能独立发现缺陷并触发修订。

技术选型的另一次 run 保留 36 claims / 32 spans，却因固定区包含全部证据在 Writer 前超限。逐字段大小统计明确了根因；把 claim 与其 span 成组筛选，brief／约束固定保留，未提供的证据不能被 Reviewer 接受。原文持久化是可回读能力，不能宣称模型获得无损无限记忆。

这些都是有 run 记录的开发问题。改进前后语料与采样没有冻结，结果只支持功能路径说明，不支持统计质量收益。

### API 和 Worker 的协议版本不同，界面一直等待

浏览器端到端联调时，本地 Worker 已输出新增的比较表引用字段，容器 API 仍用旧 Pydantic 契约，读取报告返回 422。界面原来将所有报告请求错误降为“报告未生成”，因此显示一直等待。

定位顺序：任务状态已完成 → 事件有 report.saved → API 日志显示报告 GET 422 → 对照两进程代码与 schema → 找到前端 catch 吞错。

修复：只把 404 当作尚无报告，其余错误显式展示；创建 run 时冻结非密钥配置和运行代码指纹；Worker 不匹配时中断而不调用模型；部署时同步更新 API／Worker。迁移 0003 和回归测试覆盖这条边界。属于开发联调真实问题，不包装成线上客户事故。

### OTel 标志类型阻断调用

接入真实 SDK 后，ParentBased sampler 对整数 `TraceFlags.SAMPLED` 读取 `.sampled` 报错。修复为 `TraceFlags(...)` 实例，并复测。说明观测代码本身也可能影响业务，不能只用空的 tracer stub 验证。

### 依赖和部署差异

沙箱网络让首次 pip 下载失败，不能据此推断包不存在；在独立环境获准联网后安装成功。MinIO Docker Hub 镜像不可拉取，按官方仓库示例切换 Quay 固定版本。PDF.js 参数变化由 TypeScript 构建发现，通过适配当前 API 修复而非忽略类型错误。

## 5. 恢复、重复调用和账本

Run 队列决定领取与租约，LangGraph 决定研究图内进度。父图与每个 Researcher 均有持久化 checkpoint；业务结果不能只依赖 checkpoint 写入是否完成。

外部步骤使用稳定 action ID。结果先落库而 checkpoint 尚未保存时，重放节点读取已完成响应。若进程在供应商请求完成前后崩溃但结果未保存，真实外部费用无法确定；保留预留并记 unknown，后续重试继续计费。业务有效提交可幂等，外部供应商 exactly-once 无法承诺。

故障测试真的 SIGKILL 了 Worker，分别覆盖抓取结果已存和报告响应已存的窗口；注入租约过期后，新 fence 接管，已保存调用未重复执行，累计用量保留。测试强制租约过期，不代表测得了线上故障检测时间。

取消先持久化并提高 fence，旧 Worker 不能写业务结果或 checkpoint。API 断线与取消是两件事。未完成请求可能继续计费，账本不能直接清零。

## 6. 工具遗漏与错误决策如何定位？

按链路逐层检查：brief 是否包含要求 → plan 是否建立对应任务 → 工具是否被提供 → 模型是否调用 → 参数是否合法 → 外部执行是否成功 → 来源是否被读到 → quote 是否匹配 → claim 是否通过审查 → Writer 是否引用。

V1 工具少且静态提供，不存在海量动态工具检索模块，因而不能把“工具召回率优化”写成已经完成的亮点。用户显式选择研究模板；模型不凭置信度改变业务范围。模型建议必须经过工具白名单、依赖与额度检查，语义是否选对则由覆盖 rubric 和评测判断。

目前已验证非法 JSON 重试、预算竞争、跨租户写入和进程中断等注入场景。首轮真实模型确实出现连续搜索消耗额度的行为，已按上述链路定位；其他错误决策和遗漏约束仍需积累样本，不提前编写事故故事。

## 7. 数字应该如何回答？

当前测试可以回答功能是否通过以及合成流程调用了多少次。真实任务 token、工具调用、耗时、缓存命中、成本和上下文省略比例均有记录接口；它们需要注明模型、语料、profile、样本量及重复次数。

本项目不是编程 Agent，不把完成“通用编程任务”的 token 或工具调用量当作本项目指标。研究质量评估还需人工检查所有外部事实，包括没有进入 Claim 表的断言；引用存在率不等于 citation precision。成本是版本化价格估算，并保留未知预留，不宣称与供应商账单逐分一致。

## 8. 当前限制

- 真实模型和搜索接口已连通；首轮研究发现故障并修复。大规模 heldout 和消融质量结果仍待执行。
- PDF 支持文本、页码和解析边界；图、复杂公式、扫描件及复杂表格不能保证理解正确。
- 运行部署为单 Worker 进程；进程内并发限制不代表跨机器配额能力。
- 自动审查使用同模型角色，可能共同犯错；通过门禁仍需人工复核。
- 运行工作流升级以代码指纹阻止混用，尚未提供任意版本状态迁移。
- 测试租户 API Key、RLS 与私有工件不是完整 SSO／合规认证；孤立对象清理与未知费用自动对账后置。

## 9. 如何演示而不夸大？

从 README 的 fixture 路径重建环境与两租户工作台，再查看真实 smoke 的原文、用量和未解决项。技术选型、论文理解、进程中断恢复分别使用对应脚本／测试；合成运行标明 synthetic，真实论文仍需核验实验条件。

讲 harness 时指向预算、权限、状态、验收和可观测模块；讲 memory 时区分短期子图状态、模型当次上下文、持久化资料与尚未实现的语义长期记忆。工程保证来自程序和数据库约束，语义质量来自实际评测与人工复核，不能相互替代。具体数字与样本范围统一引用 [verification-results.md](verification-results.md)。
